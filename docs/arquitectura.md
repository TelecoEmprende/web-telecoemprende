# Arquitectura

Cómo encajan backend, base de datos, frontend y despliegue. Si algo de aquí no coincide con el código, manda el código (y se corrige este documento).

## Backend y base de datos

- **`app.py`** es la entrada de Flask. Registra siete blueprints — `admin_api`, `equipo_api`, `notas_api`, `club_api`, `cron_api`, `slack_bot_api` y `marketing_api` (registrado **tres veces**, una por departamento, ver abajo) —, aplica las cabeceras de seguridad (CSP, X-Frame-Options, etc.) en `after_request` y además sirve el frontend compilado (`frontend/dist`): `/`, `/admin`, `/assets/<file>` y `/logo.png` salen del build de Vite. En desarrollo no hay otro servidor de estáticos; en Docker hay un Nginx delante (`docker-compose.yml`, Dockerfile de `frontend/`). `demo/` y `juego/` no los sirve Flask: son servicios aparte de Vercel.
- **`backend/api/admin.py`** atiende el grupo Admin de `/equipo` (ya no hay página `/admin`: `/admin/*` redirige a `/equipo`). Las inscripciones públicas están cerradas: no hay endpoint para enviarlas, solo ver, editar y exportar las que ya hay. La lógica no va en las rutas, sino en **`backend/services/`**:
  - `services/registrations.py` — CRUD de inscripciones y exportación a Excel (`openpyxl`) generada en memoria al pedirla (`generar_excel_en_memoria`); no se lee ni se escribe nada en disco.
  - `services/security.py` — límite de intentos de login (`MAX_LOGIN_ATTEMPTS_PER_WINDOW` / `LOGIN_BLOCK_WINDOW_SECONDS` en `backend/config.py`) y saneado de entradas contra inyección SQL y XSS.
  - `services/admin.py` — lee la marca de sesión `admin_auth`, que solo pone el login de `/equipo` a cuentas con `members.is_admin`. Ya no hay contraseña maestra: `POST /api/admin/login` y `ADMIN_PASSWORD` no existen.
  - `services/email.py` — correo transaccional con la API HTTP de Resend (`RESEND_API_KEY`), con plantillas por estado. Como Slack, si falta la clave o el envío falla, se ignora: nunca bloquea la operación que lo disparó.
  - `backend/schemas.py` — `build_response`, el sobre JSON común de todos los blueprints.
  - `backend/config.py` — todas las constantes que salen del entorno (URL de la base de datos, límites de campos, dominios de correo UPM permitidos, ajustes del límite de intentos).
- Las inscripciones se guardan en Postgres (tabla `registrations`); `DATABASE_URL` apunta por defecto a un Postgres local en `config.py`.
- **Esquema = `backend/migrations/NNNN_nombre.sql`**: `migrar()` (`services/db.py`) las aplica una vez cada una, en orden, en la primera petición a `/api/` de cada instancia (`before_request` de `app.py`, bajo un advisory lock de Postgres) y las apunta en `schema_migrations`. Para cambiar el esquema se añade un archivo nuevo; nunca se edita uno aplicado, y ya no hay funciones `init_*_db()`. `0001_esquema_base` es la base idempotente de lo que ya tenía producción; `0002_personas_por_id` pasó las personas a ids; `0010_tablas_y_columnas_en_ingles` lo pasó todo a inglés.
- **Nombres en la base de datos**: tablas y columnas en inglés (`members`, `club_events`, `projects`, `deliverables`, `tasks`, `task_comments`, `budget_lines`, `meetings`, `services`, `notes`, `history`, `audit_log`, `password_resets`, `registrations`; `title`, `status`, `department`, `created_by_id`...). La API y el frontend siguen en español (`titulo`, `estado`, `campaign_id`...): las vistas `<tabla>_v` exponen cada tabla **con los nombres de la API**, así que las lecturas (`SELECT * FROM tasks_v WHERE departamento = %s`) van en español y las escrituras a las tablas, en inglés. Donde un UPDATE genérico traduce campos de la API a columnas hay un mapa: `_COLUMNA` (`services/marketing.py`), `Tabla.columnas` (`services/registros.py`), `NOTA_COLUMNAS` (`services/notas.py`). Los *valores* de enumeración (`'pendiente'`, `'marketing'`, `'proyecto'`) son datos y no cambian. Renombrar una columna no rompe las vistas (Postgres las reescribe y conserva el nombre de salida); añadir una obliga a recrear su vista. Tras migrar, `migrar()` activa RLS en cualquier tabla de `public` que no lo tenga: Supabase expone `public` por su API REST a quien tenga la clave pública del proyecto, RLS sin políticas lo cierra, y al backend (dueño de las tablas) no le afecta (`tests/test_rls.py`).
- **Las personas se referencian por id de cuenta, nunca por email**: `created_by_id`/`author_id`/`edited_by_id`/`owner_id` (FK a `members.id`, `ON DELETE SET NULL`) y tablas de unión para «quién está en qué» (`task_assignees`, `deliverable_assignees`, `meeting_attendees`, `service_owners`; `ON DELETE CASCADE` en los dos sentidos, `position` guarda el orden elegido). Así, cambiar el email de alguien (editable en Cuentas) o borrar su cuenta se refleja en todas partes. La API sigue hablando con emails: las escrituras pasan por `fijar_personas`/`id_de_persona` (`services/db.py`; un email sin cuenta lanza `DatosInvalidos` → 400) y las lecturas por las vistas `<tabla>_v` (`tasks_v`, `deliverables_v`, `projects_v`, `task_comments_v`, `meetings_v`, `services_v`, `budget_lines_v`, `notes_v`), que vuelven a convertir ids en emails. Las vistas son `security_invoker`, así que heredan el RLS de las tablas. `notes.project_id` es una FK de verdad a `projects` (`ON DELETE SET NULL`). `audit_log.email` se queda como email a propósito: registra quién era en ese momento.
- **`backend/api/marketing.py`** / **`services/marketing.py`** es la API del trabajo por departamento (proyectos, entregables, tareas, calendario, carga de cada persona). Las rutas se declaran una vez, pero el blueprint se registra tres veces en `app.py` con distinto `name` (`marketing_api`, `eventos_api`, `ingenieria_api`); `departamento_actual()` lee `request.blueprint` para acotar cada consulta, así que el mismo código sirve a los tres departamentos sin duplicar rutas. Todas las rutas llevan `@requiere_sesion` (todos somos de los tres departamentos; los permisos finos se comprueban dentro de cada ruta). **Proyectos** (tablas `projects` + `deliverables` + `tasks`; la API aún los llama `campaigns`/`contents`; `CampaignsPanel`) es el mismo panel y vocabulario en los tres departamentos —un proyecto tiene *entregables* con tareas dentro— y enseña las notas enlazadas (`notes.project_id`, `NotasDelProyecto.tsx`: abrir en Notas, enlazar una que ya existe, desenlazar o crear una ya enlazada).
- **`backend/api/registros.py`** / **`services/registros.py`** añade tres entidades más (`presupuesto`, `reuniones` y `servicios`, esta solo de Ingeniería) como rutas colgadas directamente de `marketing_api`. Se importa en `app.py` solo por ese efecto, y *antes* de registrar el blueprint (Flask no deja añadir rutas a uno ya registrado). Todas usan un mismo montaje CRUD genérico (`_montar_rutas`) y heredan la autenticación y el acotado por departamento de `marketing_api`; los campos URL (`url`, `linkedin`) pasan por `_url`, que rechaza todo lo que no sea http(s), para que un enlace `javascript:` guardado nunca llegue a un `<a href>`. `GET /plataforma` (`services/plataforma.py`) cuelga del mismo blueprint pero solo responde en `/api/ingenieria` (404 en los demás, incluso con sesión de admin): commit y rama desplegados según las variables `VERCEL_*` de Vercel, un `SELECT 1` y, por integración, si su variable de entorno está puesta (solo booleanos, nunca el valor).
- **`backend/api/notas.py`** / **`services/notas.py`** — Notas (páginas tipo Notion, JSON de BlockNote en `notes.content` JSONB). Blueprint propio, `notas_api`, bajo `/api/equipo` (no por departamento): cada nota es de todo el club (`departamento = ''`), de un departamento del autor o privada (solo el autor). La visibilidad se aplica en el WHERE de cada consulta (`_visible`), solo el autor cambia la privacidad, y todo `href`/`url` dentro de los bloques tiene que ser http(s)/mailto. El listado devuelve un `resumen` en texto plano y las casillas sin marcar (`pendientes`), que es lo que enseña la tarjeta «Pendiente en notas» del Inicio: las notas sirven también de lista de pendientes del club.
- **`services/luma.py`** — próximos eventos del calendario público de Luma del club (`LUMA_CALENDAR_ID`/`LUMA_CALENDAR_URL` en `backend/config.py`, por defecto https://luma.com/alumni.etsit.upm), leídos de su feed iCal abierto (sin clave), con caché de 15 min en memoria y fallo silencioso como el correo y Slack. Se sirve en `GET /api/equipo/luma`; los «Próximos eventos» del Inicio y la tarjeta de próximo evento del sidebar los mezclan con el calendario del club y enlazan cada uno a su página de Luma («Apuntarme»). En local, el Python de python.org para macOS no trae certificados: hay que arrancar el backend con `SSL_CERT_FILE=$(python -m certifi)` o el feed vuelve vacío sin avisar.
- **`backend/api/cron.py`** — dos tareas que solo lanza Vercel Cron (ver `vercel.json`), autorizadas con la cabecera bearer `CRON_SECRET` (nunca con cookie de sesión). `POST /api/cron/avisar-deadlines` (diario, 08:00) avisa por Slack de las tareas que vencen mañana en todos los departamentos y de las reuniones de mañana, y luego limpia: papelera de más de 30 días, auditoría e inscripciones sin cuenta de más de un año. `POST /api/cron/resumen-equipo` manda los lunes el resumen de la Mesa del club.
- **`services/auditoria.py`** — registro de auditoría de `/equipo`: un `after_request` de `app.py` apunta cada POST/PUT/PATCH/DELETE bajo `/api/` (salvo el cron y el bot de Slack) y las descargas de datos personales (Excel/PDF), con quién (el email de la sesión, tomado en `before_request` para que el logout siga teniendo nombre; en un login fallido, el email intentado), método, ruta, estado e IP, nunca el cuerpo de la petición. Falla en silencio. Lo leen los admins en **Auditoría** (`GET /api/admin/auditoria?q=`, `AuditoriaPanel.tsx`, que convierte cada ruta en una frase con `describir`).
- **`services/slack.py`** — avisos al canal del club por Incoming Webhook (`SLACK_WEBHOOK_URL`): tareas creadas, cambios de estado, comentarios, lo que vence mañana, reuniones convocadas y las de mañana, y el resumen de los lunes. Con `SLACK_BOT_TOKEN`, menciona a responsables y convocados buscando su cuenta por email (`users.lookupByEmail`, necesita el permiso `users:read.email` en la app de Slack); sin él, pone el nombre. Falla en silencio como `services/email.py`.

## Frontend

- `frontend/src/routes/EquipoPage.tsx` es toda la página `/equipo` (comprobar sesión → login o espacio de trabajo). El sidebar (`EquipoSidebar.tsx`, shadcn `variant="floating"`, con estilos bajo `.crm-sidebar-react` para que también se apliquen en el Sheet del móvil) se agrupa en Inicio (Inicio = `CalendarioEquipo.tsx`, la portada; Mesa del club; Notas) / Trabajo (Tareas, Proyectos, Calendario) / Club (Miembros, Reuniones, Herramientas, Papelera) / Admin; `seccionesDe` asigna cada sección a su grupo. El elemento activo es una píldora Noche compartida con `layoutId` de motion que se desliza entre entradas. `components/equipo/notas/*` tiene `NotasPanel` (lista + editor que guarda solo) y `NotaEditor` (BlockNote + Mantine, cargado bajo demanda para que solo se descargue al abrir una nota). `components/equipo/DeptoDashboard.tsx` es común a los tres departamentos (solo cambia `depto`, más `teams` con todos los de la persona); `components/equipo/marketing/*` tiene los paneles de Proyectos, Tareas y Miembros y `CalendarPanel` (se llama `marketing/` por historia: lo usan los tres); `components/equipo/registros/*` es el panel genérico (`RegistrosPanel`) de las tres entidades de `registros`, configurado en `paneles.tsx`, más `ReunionesPanel`. `PANELES_POR_EQUIPO` (`EquipoSidebar.tsx`) decide qué paneles por departamento ve cada persona (Plataforma y Servicios de Ingeniería están dentro de Herramientas; el botón de GitHub del pie del sidebar sale a quien tiene Ingeniería, `GITHUB_REPO` en `types/equipo.ts`). El calendario no es uno de ellos: como ya enseña y filtra los eventos de todos los departamentos en una pantalla, hay una sola entrada «Calendario» por persona. `CalendarPanel` usa `teams` para saber qué es «solo lo mío», y abrir desde él un elemento de otro departamento lleva a Proyectos con el mismo mecanismo que los enlaces compartidos (`?campaign=`), que busca el proyecto en los tres departamentos.
- **`/equipo` es la única parte del código con Tailwind + shadcn/ui** (`components/ui/*`; se añaden con `cd frontend && npx shadcn@latest add <componente>`); el resto es CSS plano escrito a mano (ver abajo). El reset de Tailwind está desactivado a propósito (`index.css` importa `tailwindcss/theme.css` y `tailwindcss/utilities.css` por separado, no el `@import "tailwindcss"` completo) para que no afecte a la web pública, y las clases de Tailwind solo hacen efecto dentro del contenedor `.shadcn-scope` (la raíz de `/equipo`), que reasigna los 6 tokens que espera shadcn (`--color-primary`, `--color-background`, etc.) a los valores de `tokens.css`, así que los dos sistemas comparten paleta. Para `/equipo` no se tocan `landing.css`/`inicio.css`/`admin.css`: se usa `equipo.css` o clases de Tailwind.
- **El movimiento del CRM (`/equipo`) sale todo de `frontend/src/components/movimiento.tsx`**, construido sobre las constantes de [SmoothUI](https://smoothui.dev) (`components/smoothui/lib/animation.ts`, instalado con `npx shadcn@latest add @smoothui/<nombre>` — el namespace `@smoothui` ya está en `components.json`). Exporta `PanelAnimado` (entrada al cambiar de sección), `FilaAnimada`/`useEntradaDeFila` (entrada escalonada + recolocación de tarjetas, filas y `<tr>`) y `Contador` (números que ruedan al cambiar). Reglas al añadir animaciones nuevas: solo `transform` y `opacity`, 0,2-0,3 s, muelle `bounce` 0,1, y `useReducedMotion` siempre respetado. Dos avisos que ya costaron un rato: `motion.button` se queda con `onDragStart`/`onDragEnd` para su propio sistema de arrastre, así que lo que use drag nativo (el tablero de `TasksPanel`) se envuelve en un `motion.div` en vez de convertirse; y una barra de progreso no puede llevar a la vez `transition: transform` en CSS y una animación de motion — las dos capas se pelean y el avance se queda a medias. Los componentes de SmoothUI que traen `tokens.json` (`animated-tabs`, `notification-badge`) meten en `index.css` una paleta rosa + grises propia que no es la de marca: tras instalarlos hay que revertir `index.css` y repuntar sus clases a `tokens.css`.
- **Rutas del frontend** (`frontend/src/App.tsx`): una tabla plana de `react-router-dom`: `/` (`HomePage`), `/news` (`NewsPage`), `/privacidad` (`PrivacyPolicyPage`), `/equipo` (`EquipoPage`), `/admin/*` (un `<Navigate>` a `/equipo`) y un `NotFoundPage` para todo lo demás.
- **`HomePage`** monta la portada con las secciones de `components/home/*` en orden (Hero, About = «El club», LatestNews, Departments, Events, Recursos, Team, Closing) más `LandingNav`/`LandingFooter`. `ClosingSection` (`#comunidad`) lleva a la comunidad de WhatsApp y a Instagram; la tarjeta de «próximo evento» de `EventsSection` enlaza a Luma. Los eventos pasados están en `data/events.ts` y los recursos recomendados (vídeos, cursos, podcasts, webs) en `data/recursos.ts`: se añade un objeto al array y la sección lo pinta. Las secciones de la portada tienen sus estilos en `styles/inicio.css` (prefijo `in-*`) y se animan con `components/home/aparece.tsx` (`Aparece`, `TitularAnimado`: al hacer scroll, una vez, solo `transform`/`opacity`, respetando el movimiento reducido); las cifras salen de `CLUB_EVENTS` y de la lista del equipo, nunca escritas a mano. **La sección Team no es una lista en el código**: lee las cuentas de `/equipo` marcadas «Sale en la web» en Cuentas del equipo (`members.on_website`) por el endpoint público `GET /api/equipo/miembros-web` (`listar_miembros_web`: solo cuentas que además tienen foto subida; solo viajan nombre, primer apellido y foto, nunca email, DNI ni departamentos), compartido con la cifra de «personas en el equipo» por `useMiembrosWeb`. Así, una foto o un nombre cambiados en Cuentas cambian también en la web. Las fotos se guardan enteras, sin recortar (`aFotoPerfil` en `utils/imagen.ts`: lado mayor 800 px, data URL JPEG en `members.photo`, servida al navegador como `/api/equipo/foto/<id>?v=`); la tarjeta de la web las recorta a 4:5 con `object-position`, en gris hasta pasar el ratón, y los avatares redondos del CRM con `object-cover`. Hay tres componentes de [React Bits](https://reactbits.dev) en `components/reactbits/` (RotatingText en el hero, Magnet en los botones principales vía `Iman`, CircularText en el anillo del cierre), **copiados a mano, no con `shadcn add @react-bits/...`**, porque ese registro fija `motion@^12` y bajaría el `motion@13` que usa el CRM; se coge la variante TS-CSS (Tailwind no aplica fuera de `.shadcn-scope`) y se quitan colores/sombras fijos y nombres de clase globales genéricos. Los estilos son CSS plano en `frontend/src/styles/*.css` (`inicio.css` para la portada, `landing.css` para la navegación, el pie, `/news`, privacidad y páginas de error, `news.css` para `/news`, `admin.css` para las tarjetas de Admin, `tokens.css` para las variables comunes), escrito a mano, sin framework ni módulos CSS (prefijos `in-*`/`lp-*` en la web pública, sufijo `*-react` en las zonas internas). `/equipo` es la excepción: ver Tailwind/shadcn arriba.
- **Marca**: `docs/brand-guide.html` es la referencia (v2: Azul TE `#1350b8`, Impulso `#e0680e`, Chispa `#f4b044`, Noche `#112532`, neutros Papel; **Anton** para titulares, solo peso 400, e **Inter** 400-700 para texto e interfaz — ver `DESIGN.md`). Todo color de `frontend/` (portada, `/admin`, `/equipo`) pasa por `tokens.css`; no se escribe a mano ningún hex ni `rgba()` en un componente ni en una hoja de estilos. `demo/` y `juego/` son servicios independientes de Vercel que no comparten CSS con `frontend/`: cada uno tiene su propia copia de la paleta como propiedades con hex literales (`juego/game.css`, `demo/src/index.css`), así que un cambio de color de marca hay que hacerlo a mano en los tres sitios. Cada departamento tiene su color (Tech = Azul, Marketing = Impulso, Eventos = Noche, en `--color-depto-*`). La navegación usa el logo todo blanco (`public/logo-blanco.png`); `public/logo.png` es el de color (favicon, og:image, CRM).
- **Vistas de Admin** (`components/admin/*`): son secciones normales de `/equipo`; cada una carga sus datos y enseña su propio `AlertBanner`. Los filtros de inscripciones (`evento`, `estado`, `q`) van en la URL con `useSearchParams`. Añadir una supone un id de `Seccion` + entrada en `itemsAdmin` (`EquipoSidebar.tsx`), su título en `TITULO_ADMIN` y su línea de render en `EquipoPage.tsx`; las rutas del backend usan `@requiere_admin` (`backend/api/sesion.py`). `admin.css` solo tiene los estilos de tarjeta que usan esas vistas.
- Los tests del frontend son Vitest + Testing Library (`src/test/setup.ts`), junto al componente como `*.test.tsx` (ver `components/admin/InscripcionesView.test.tsx`, `components/equipo/DeptoDashboard.test.tsx`). Los del backend son `unittest`, un archivo por área en `tests/` (`test_marketing.py` es el más grande; `test_migraciones.py` repite las migraciones en una base de datos de prueba para comprobar que los datos sobreviven).

## Despliegue en Vercel

El repo se despliega en Vercel con `vercel.json`, que define cuatro **servicios**: `backend` (esta app de Flask, `framework: flask`, `entrypoint: app.py`, `root: .`), `frontend` (el build principal de Vite, `root: frontend/`), `demo` (`root: demo/`) y `juego` (`root: juego/`, sin framework ni build). Las reescrituras de primer nivel mandan `/api/*` a `backend`, `/demo` y `/demo/*` a `demo`, `/juego` y `/juego/*` a `juego`, y todo lo demás a `frontend`; `demo` y `juego` tienen además su propia reescritura que quita el prefijo antes de caer en su `index.html`. `vercel.json` declara también los cron (ver `backend/api/cron.py`) y las cabeceras de seguridad de producción (CSP, HSTS, etc.; en local y Docker las pone el `after_request` de `app.py`). Postgres es Supabase, dado de alta con la integración del Marketplace de Vercel (`vercel integration add supabase`), que inyecta `POSTGRES_URL`/`POSTGRES_URL_NON_POOLING`, etc.

El servicio `frontend` reescribe `/(.*)` a `/index.html`, así que una ruta solo de cliente no da 404 en Vercel. Lo que aporta cada `frontend/<ruta>/index.html` (la misma carcasa con otro `<title>`/meta, como entrada extra de Rollup en `build.rollupOptions.input` de `frontend/vite.config.ts`) es un título y una descripción de verdad para esa URL: un archivo estático gana a la reescritura. Por eso una ruta nueva **de primer nivel** quiere su propio `index.html` + entrada para el título de la pestaña y las vistas previas de enlaces; las rutas anidadas caen en el `index.html` principal y no lo necesitan. El servidor de desarrollo de Flask no tiene ese respaldo: las rutas que no declara dan 404 en local (ver la ruta `/admin/<vista>` de `app.py`). Docker/nginx ya hace `try_files ... /index.html`.
